# 串门互动协议设计

当前方向已调整为发送端创作、接收端播放。见 [Generative Message 设计](generative-message.md)。下文保留为早期方案。

在现有拜访会话里发送自由意图。发送端把用户的话整理为结构化请求，Relay 管会话和投递，接收端用自己的角色素材和渲染器现场生成效果。以下是设计稿，现有口信版继续使用原接口。

```json
{
  "version": 1,
  "visitId": "visit_123",
  "requestId": "req_456",
  "mode": "joint",
  "intent": "轻轻拥抱一下，庆祝项目上线",
  "fallbackText": "想抱一下，庆祝项目上线。"
}
```

`mode` 表示是否需要双方参与。`solo` 可以展示访客送花、挥手或独舞。`joint` 用于拥抱、亲吻或共舞，每次都由对方确认。动作内容用自由文本表达。同一份协议可以承载新的互动，服务端按参与方式和会话规则处理。

1. A 先发起拜访，B 请进后，A 可以发送互动意图。Relay 从设备令牌识别发送方，按拜访记录确定接收方，校验会话仍有效并按请求编号去重。
2. B 先看到口信。涉及 B 的角色时，B 的客户端展示具体请求，接受后才生成双人效果。即使 A 把请求标成 `solo`，接收端也只允许它操纵访客和独立道具。需要 B 参与的效果必须走 `joint` 确认。
3. B 的模型根据意图和本地支持的角色、道具和动画生成一段声明式场景。播放器校验角色权限、动作范围、时长和元素数量后播放。外部意图和模型输出都按数据处理，播放器只接受本地支持的组件和字段。
4. B 可以拒绝或结束拜访。拒绝只结束这次互动，送客则使会话内未完成的互动失效。播放前再次核对会话状态，避免模型生成得慢、访客离开后才弹出动画。

建议在现有拜访 API 上新增互动创建、按游标读取和接受或拒绝操作。Relay 记录互动请求和决定，仅参与者可读取。同一请求的重试返回原结果。客户端按事件 ID 去重，重连后补收记录，已过期的事件只保留文字历史。

开源无头 Client 提供收发、同步和确认接口，并可直接输出文字。桌面版或第三方界面订阅同一事件，自行决定用模型生成场景、用预制动画，还是只显示文字。生成失败或缺少素材时保留原口信。首轮用送花验证单方效果，再用拥抱验证双方确认和超时，亲吻和共舞可以走同一条链路。
